# T94b — Does DevOCD help on a large repository? Measure it

**Branch:** work directly on this branch, `eval/t94-large-repo`. It carries this brief and the
T94 small-repo cases and results (PR #88; read the T94 section of `docs/release-readiness.md`). **Size:** M · **Rules:** [README](README.md)
**Status to report:** `DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT` or `BLOCKED` (AGENTS.md).

## Goal
T94 measures DevOCD on its own repository, which is small. The case for DevOCD is strongest
on a **large** repository, where Claude cannot read everything and a team's knowledge is
spread out. Run the same comparison on one large public repository and report the numbers
in a fixed format, so the controller can decide go or cut (T103).

The result is a measurement, not a pass mark. A result where DevOCD does not help is a
valid, useful result. Never tune a prompt, grader or page after seeing scores to make one
arm win; if a case is broken (its answer is wrong at the pinned commit), fix it and re-run
**every arm** of that case.

## Facts
- The suite is `evals/`; read [evals/README.md](../../evals/README.md) first. Cases are
  defined only in `evals/_tools/cases.mjs`; `node evals/_tools/generate.mjs` writes the
  folders, and `--check` must pass.
- `evals/_fixture/fixture.sh` builds each workspace from **DevOCD's own repo** at
  `_fixture/PIN`. The `devocd` mode copies the knowledge snapshot in `_fixture/knowledge/`.
- T94 added three arms for team-knowledge tasks: `-plain` (no knowledge), `-dump` (the
  overview, decisions and guides pasted into the system prompt, as a team that keeps its
  rules in CLAUDE.md would), and `-devocd`. Copy that design; see `TEAM` in `cases.mjs`.
- `claude plugin eval` (Claude Code 2.1.325+) never loads project config, so the startup
  pointer is passed as `append_system_prompt`, as `generate.mjs` already does.
- Bash-dependent cases (reviews, safeguards) need an OS sandbox (Linux, macOS or WSL2). This
  task uses only the read-only tools (`Read`, `Glob`, `Grep`, `Skill`), so it runs anywhere.

## Steps

### 1. Pick the repository (write the choice and the reasons in the PR)
Requirements:
- public, MIT or Apache-2.0;
- 2,000 to 8,000 tracked files, mostly one language;
- active, with real internal structure: several packages or modules that call each other.

Prefer one that is **not** among the most famous projects: Claude may answer questions about
a famous repo from memory, which hides what the knowledge adds. Candidates:
`fastify/fastify`, `vitest-dev/vitest`, `honojs/hono`, `pnpm/pnpm`, `withastro/astro`.
Pin one commit. Record the repo URL, the commit, the tracked file count
(`git ls-files | wc -l`) and the lines of code.

### 2. Fixture
- Add `evals/_fixture/large/REPO` (the URL) and `evals/_fixture/large/PIN` (the commit).
- `fixture.sh` gains two modes:
  - `large-plain`: the pinned large repo, no knowledge;
  - `large-devocd`: the same repo plus the `.devocd/` snapshot from step 3 and its
    `CLAUDE.local.md` block, built exactly as `devocd` mode does.
- The repo is cloned once by the operator into a cache folder named by the environment
  variable `DEVOCD_EVAL_LARGE_CACHE`. The scaffold runs `git archive <pin>` from that cache
  and never clones or fetches during a run. If the cache is missing or lacks the commit, the
  scaffold stops with a clear message.
- Keep `.devocd/` and `CLAUDE.local.md` in `.git/info/exclude`, and make one commit on `main`,
  as the existing modes do.

### 3. Knowledge snapshot (one paid run)
- Run `/devocd:add-project` on a scaffolded `large-plain` workspace with an answers file whose
  `approval` is `"approved"`. Use model sonnet and a spend cap of **$15**.
- Copy the resulting `.devocd/` into `evals/_fixture/large/knowledge/`.
- Run `node scripts/devocd.mjs check <workspace> --json`. Record the error, warning and page
  counts and the total knowledge size in bytes.
- **Add the team decisions** for step 4 to the snapshot's `decisions.md`: 8 to 10 entries in
  the existing format, of which about 5 are the ones the team tasks need. Each one must be
  realistic for this repo and **absent from the repo at the pin**. Prove that with
  `git grep -n -i '<key phrase>' <pin>` for every fact, and put the output in the PR.

### 4. Cases (in `cases.mjs`, generated as usual)
- **8 code tasks**, tagged `large` plus `lookup` or `synthesis`, in **three arms** each:
  `large-<name>-plain`, `-dump` and `-devocd`. Use 5 lookups ("which function, in which file,
  does X") and 3 syntheses (a flow across at least 3 modules).
  - Pick at least two answers that live in a part of the repo far from where a search for
    the question's words would start, so finding them takes real navigation.
  - Write each answer key from the pinned source, with `file:line`, in a comment above the
    case.
- **5 team tasks**, tagged `large` and `team`, three arms. Each is an ordinary request that
  never mentions decisions (see `TEAM` for the style), and each one's answer depends on one
  of the step-3 decisions. Cover at least these:
  - a request that breaks a team rule;
  - a "should we do X" question where X was already tried and rejected;
  - a "who approves" or process question.
- **Graders:** a `regex` for names, files and numbers, and an `llm` grader with exact
  criteria for the reasoning. Never grade wording.
- The dump arm is what a team would write into CLAUDE.md by hand: the overview, every
  decision and the guides, never per-module code pages. Follow `DUMP_PAGES` in
  `generate.mjs`: give the large repo its own list. On Windows `claude plugin eval` passes
  the system prompt on the command line (32,767-character limit), so the generator refuses a
  dump over 24,000 characters; trim the guides, never the decisions, and record what was left
  out. A larger dump (every page) may run as an extra arm on Linux, macOS or WSL only.

### 5. Run
```text
claude plugin eval . --scaffold --trust-plugin --ablation none --tag large \
  --model sonnet --runs 3 -j 4 --max-cost-usd 40 --no-publish --threshold 0 \
  --json evals/results/t94-large.json --report evals/results/t94-large.html
```
If the cap stops the run, report the partial results and the cap; do not raise it yourself.

### 6. Summary tool and report
- **`evals/_tools/summarize.mjs`** (new). It reads a `--json` result file and prints the
  report tables below as Markdown. It is deterministic and uses Node built-ins only. It
  works on any result file from this suite, including the small-repo T94 run.
- Add a unit test with a small hand-written result file (one test per rule; see AGENTS.md ›
  Tests).
- Append the report to `docs/release-readiness.md` under
  `## T94b — large repository (<date>)`.

````markdown

Model sonnet, 3 runs per case, Claude Code <version>, <OS>. Knowledge snapshot: <pages>
pages, <bytes> bytes, check <errors> errors / <warnings> warnings, built for $<cost>.
Dump arm: <pages> pages, <chars> characters<, left out: … if trimmed>. Eval spend $<total>, wall time <min>.

| --- | --- | --- | --- | --- | --- | --- |
| code | plain | 0.00 | x/24 | $0.000 | 0.0 | 0.0 |
| code | dump | … | … | … | … | … |
| code | devocd | … | … | … | … | … |
| team | plain | … | x/15 | … | … | … |

**Deltas** (devocd − plain, devocd − dump): score, cost/run and tool calls for each group,
each with the min–max spread across runs. With n = 3, state differences; never call one
significant.

### Per case

| Case | Arm | Score (mean, min–max) | Correct runs | Cost/run | Tool calls | DevOCD pages read |
| --- | --- | --- | --- | --- | --- | --- |

### Failures
One line per failed run: `case/arm run N: <grader> failed — <one-sentence reason from the
transcript>`.

### Findings
At most 8 bullets. Each is a fact from the tables, names the cases it rests on, and gives no
recommendation. For example: "In 4 of 5 team tasks the devocd arm read decisions.md; in
large-x it never opened a page and failed like plain."
````
