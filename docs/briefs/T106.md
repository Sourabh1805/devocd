# T106 — Commits credited to the right GitHub account

**Branch:** `fix/commit-identity`, from current `main`.
**Size:** M · **Rules:** [README](README.md) · **Needs:** nothing.
**Never push history.** Part B ends with a rewritten copy for the user to push. You push only
the Part A branch.

## Goal
GitHub credits 10 commits in this repo to someone else: the stranger whose GitHub login is
`sourabh`. Rewrite those 10 commits so they're credited to the owner (Part B). Add a check
that keeps a wrong identity from getting in again (Part A).

## Facts
- GitHub credits a commit to an account by its email. `<login>@users.noreply.github.com`
  belongs to the account `<login>`. The owner's address is
  `35189997+Sourabh1805@users.noreply.github.com` (numeric ID + login).
- 10 commits use `Sourabh Gavali <sourabh@users.noreply.github.com>` as both author and
  committer. All are "docs: link Txx to PR #nn" from 2026-11-20 16:37–17:43 UTC, from
  `992bdec` (T28, #49) to `de1c7f4` (T92, #58). Check this with
  `git log --all --format='%h %ae %ce %s' | grep 'sourabh@users'`.
- Only commits on the default branch (`main`) count toward the contribution graph. But
  about 30 other branches contain those commits, so every branch has to be rewritten the
  same way. Otherwise the next merge brings the old commits back.
- 114 commits on `main` come after `992bdec`, so all of them get new hashes. 31 of those
  are merge commits signed by GitHub, and a rewrite removes their "Verified" badge. The
  owner has accepted that.
- `evals/_fixture/PIN` holds `6b5d6d9`, a commit after the bad ones, so its hash changes.
  CI checks out with `fetch-depth: 0` so the eval suite can reach that commit.
- Leave `T46 implementer <t46@example.invalid>` alone (1 commit). No account can claim
  that address.
- GitHub keeps `refs/pull/*/head` for every PR, and nobody can rewrite them. They don't
  count toward contributions, so leave them as they are.
- Open PRs right now: #79 (`test/hook-timing`), #81 (`feat/prompt-once` → `brief/T74`).
  Force-pushing their branches updates those PRs.

## Part A — the check (a normal PR)
1. `tests/tools/authors.mjs` exports `badIdentities(entries)`. `entries` is a list of
   `{ hash, author, committer }` emails. It returns every entry with an email that
   - matches `^[^+@]+@users\.noreply\.github\.com$` (case-insensitive): a login-only
     noreply address, which GitHub credits to whoever owns that login; or
   - ends in `.invalid`, `@example.com`, `@example.org`, `@localhost` or `.local`.

   `noreply@github.com` (GitHub's own web merges) and `<digits>+<login>@users.noreply.github.com`
   pass. So does any other ordinary address.
2. CLI: `node tests/tools/authors.mjs <base> <head>`. It reads
   `git log --format=%H%x09%ae%x09%ce <base>..<head>`, prints one line per bad commit
   (`<short hash> author=<email> committer=<email>`) and exits 1 if there are any.
   Otherwise it exits 0 with no output. Wrong arguments exit 2.
3. In `ci.yml`, add a step that runs only on `pull_request` and only on `ubuntu-latest`:
   `node tests/tools/authors.mjs ${{ github.event.pull_request.base.sha }} ${{ github.event.pull_request.head.sha }}`.
   It checks only the PR's own commits, so the 10 old ones don't fail every PR before
   Part B is pushed.
4. Add this bullet to AGENTS.md under Repository workflow: *Commit with the repository's
   git config. Never set an author or committer name or email yourself (no `-c user.*`,
   no `GIT_AUTHOR_*`/`GIT_COMMITTER_*`, no `--author`). CI rejects identities GitHub would
   credit to someone else.*
5. Add a trap line to repo-memory.md: a login-only noreply email credits the commit to a
   stranger, and fixing that means rewriting history (T106).

## Part B — the rewrite (prepared and verified, never pushed)
Use a scratch folder outside the repo, e.g. `D:\work\devocd-rewrite\`.
1. `python -m pip install git-filter-repo`.
2. `git clone --mirror https://github.com/Sourabh1805/devocd.git old.git`. Make a backup
   first: `git -C old.git bundle create ../devocd-backup.bundle --all`. Then
   `git clone --mirror old.git new.git` (Part B never fetches from GitHub again).
3. In `new.git`, delete the `refs/pull/*` refs (they can't be pushed):
   `git for-each-ref --format='delete %(refname)' refs/pull | git update-ref --stdin`.
4. Write `mailmap` with exactly this one line:
   `Sourabh Gavali <35189997+Sourabh1805@users.noreply.github.com> <sourabh@users.noreply.github.com>`
   Then run `git -C new.git filter-repo --mailmap ../mailmap --force`.
5. **Verify.** Every check has to pass. Paste each one's output into the PR:
   - same branch names in `old.git` (excluding `refs/pull`) and `new.git`;
   - for every branch, the same `git rev-list --count` and the same tip tree
     (`git rev-parse <branch>^{tree}`) in old and new;
   - `git log --all --format='%ae%n%ce' | sort -u` in `new.git` doesn't contain
     `sourabh@users.noreply.github.com`;
   - diff `git log --all --format='%T|%an|%ae|%ad|%cn|%ce|%cd|%P-count|%s'` between old
     and new, sorted, with the parent hashes replaced by their count. Exactly 10 lines
     differ on each side, and only in the two email fields;
   - the new hash of `6b5d6d9`, from `new.git/filter-repo/commit-map`;
   - the new tip hash of `main`.
6. Write `push.md` in the scratch folder and paste it into the PR. It tells the owner to:
   - announce the rewrite and make sure nobody pushes during it;
   - turn off branch protection on `main` if it blocks force-pushes;
   - point `new.git` at GitHub
     (`git -C new.git remote set-url origin https://github.com/Sourabh1805/devocd.git`) and
     push the branches only: `git -C new.git push --force origin 'refs/heads/*:refs/heads/*'`.
     Don't use `--mirror`: it would delete branches that exist only on GitHub and would try
     to push refs that filter-repo leaves behind;
   - re-clone their local working copy (`d:\work\DevOCD`) rather than resetting it, and
     do the same on every other machine and for every worker;
   - expect the contribution graph to update within 24 hours.
7. Write the follow-up in `push.md`. After the push, a one-line PR changes
   `evals/_fixture/PIN` to the new short hash of `6b5d6d9`. The controller opens it
   because Part A doesn't own that file. Until it merges, the eval suite can't find its
   pinned commit.
