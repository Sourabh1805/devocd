# T60 — One contract test for every skill, safeguards kept

**Branch:** `test/skill-contract` · **Size:** M · **Rules:** [README](README.md)

## Goal
Skill tests today mostly pin wording: about 160 `assert.match` / `includes` checks on
`SKILL.md` and reference text across five files. A reworded sentence breaks them, and a
missing rule in a skill nobody wrote a test for goes unnoticed. Replace them with:
1. **one generic contract** that every skill under `skills/` must pass, and
2. **one safeguard table per skill**, holding only the wording checks that protect the user.
   Style checks are deleted.

## Facts
- Skills: `skills/<name>/SKILL.md` plus optional `skills/<name>/references/*.md`. Today there
  are eight: add-project, capture, check, company-policy, install, pr-review, refresh, setup.
- Grants sit in the frontmatter `allowed-tools:` list, for example
  `Bash(node "${CLAUDE_PLUGIN_ROOT}/scripts/devocd.mjs" refresh-status *)`. The body and its
  references run helper commands as `node "${CLAUDE_PLUGIN_ROOT}/scripts/devocd.mjs" <cmd> …`.
- Every skill has `$ARGUMENTS` in its body once (for example `Input: $ARGUMENTS`).
- `tests/unit/plugin-contract.test.mjs` already checks the Agent Skills spec, the
  100-line/900-token budget, the always-on listing and a few per-skill grants
  (pr-review, install, check). Keep those tests; do not duplicate them.
- Wording tests live in `add-project-skill`, `company-policy-skill`, `install-skill`,
  `pr-review-skill` and `setup-skill` (`tests/unit/*-skill.test.mjs`). Some tests in those
  files run code (import from `scripts/lib`, spawn the CLI, build a workspace); those are
  **not** wording tests.

## Owns
- `tests/unit/plugin-contract.test.mjs` (add the generic contract)
- `tests/unit/skill-safeguards.test.mjs` (new)
- `tests/unit/add-project-skill.test.mjs`, `company-policy-skill.test.mjs`,
  `install-skill.test.mjs`, `pr-review-skill.test.mjs`, `setup-skill.test.mjs`
- `docs/TASKS.md` (T60 line only)

**No changes under `skills/`, `agents/`, `scripts/` or `hooks/`.** If the contract finds a
real mismatch in a skill, record it as described in step 2 and report it; do not fix the skill.

## Steps
1. **Generic contract** in `plugin-contract.test.mjs`: a loop over every folder in `skills/`
   (read the folder, do not hard-code the list), one `test()` per skill per check:
   - **a.** every `devocd.mjs <cmd>` the body or its references run has a matching
     `Bash(... devocd.mjs" <cmd> *)` grant, and every such grant is run somewhere in the
     body or references (grants equal commands);
   - **b.** every `references/<file>` the body links or names exists, and every file in
     `references/` is named by the body or by another reference (no orphan);
   - **c.** `$ARGUMENTS` appears exactly once in `SKILL.md`.
2. **Known gaps.** If a check fails on today's skills, do not weaken the check. Add the exact
   pair to a `KNOWN_GAPS` table at the top of the contract block, for example
   `{ skill: 'refresh', check: 'grant', item: 'backup', why: 'run in incremental.md, not granted' }`,
   skip only that item, and list every row in the PR under **Concerns**. A row whose gap
   no longer exists must fail the test (so the table cannot go stale).
3. **Sort every wording assertion** in the five `*-skill` files into exactly one class:
   - **safeguard:** the text states a rule that protects the user or their files. Approval
     before writing, never fabricate approval, write and delete scope, never touch a team
     file, refuse links or unsafe folders, secrets never echoed, read-only modes, a budget
     or limit the model must respect, a command the skill must not run or grant.
   - **style:** anything else. A heading name, a section order, a phrase, a file being
     mentioned, an example's wording, a tone.
   - **When unsure, it is a safeguard.**
4. **Move safeguards** into `skill-safeguards.test.mjs` as one table per skill:
   `const SAFEGUARDS = { setup: [{ rule, file, match, absent? }], … }`, where `rule` is one
   plain sentence, `file` is `SKILL.md` or `references/<name>`, `match` is the existing regex
   (unchanged), and `absent: true` marks a `doesNotMatch`. One loop makes one `test()` per row
   named `<skill>: <rule>`. Keep the regex exactly as it was; do not loosen it.
5. **Delete style assertions.** Delete a test when nothing is left in it. Tests that run code
   stay in their file unchanged. A `*-skill` file left with no tests is deleted.
6. Run the suite. Then, for three safeguard rows of your choice, delete the matched sentence
   from a scratch copy of the skill text in memory (not on disk) and show that row fails;
   put the three in the PR.

## Done when
- `npm test` and `node scripts/validate-plugin.mjs` pass.
- Every skill folder passes contracts a–c, apart from listed `KNOWN_GAPS` rows.
- The PR has a table of **every deleted assertion**: file, the regex, one-line reason. The
  controller reviews each one; a deletion with no reason is reverted.
- The PR states the counts: wording assertions before, safeguard rows after, deleted, and
  test count and suite time before and after.
- T60 ticked in `docs/TASKS.md` with the PR link.
